# Google sign-in feasibility and account-linking research

Research date: 2026-09-27 (America/Sao_Paulo). The target worktree's manifest pins Better Auth `1.6.25`; the installed package in the main checkout is also `1.6.25`. External documentation below was checked on the research date unless a publication/update date is stated.

## Finding

Google sign-in is feasible with Better Auth, but login and registration must be separate intents. `/entrar` should start Google sign-in without `requestSignUp`; `/cadastro` may explicitly set `requestSignUp: true` when the Hub's public-signup flag permits it. `disableSignUp: true` would block registration through Google too, so it conflicts with the product clarification. `disableImplicitSignUp: true` supports the desired separation, provided the signup flag is also enforced server-side for explicit social-signup requests.

Hub's identity guide says public signup defaults off, purchase-created users remain `email_verified=false`, and buyer matching canonicalizes some provider aliases. Better Auth 1.6.25 lowercases the OAuth email for exact matching but does not apply Hub's buyer normalizer. Its existing route guard blocks only `POST /sign-up/email`; explicit social signup is a separate path. See [`identity-and-authorization.md`](../docs/domain/identity-and-authorization.md), the current [auth route](../src/app/api/auth/%5B...all%5D/route.ts), and the [version-pinned Better Auth callback and account-linking source](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/better-auth/src/oauth2/link-account.ts) (accessed 2026-09-27).

## Better Auth behavior: documented facts

- The Google provider uses the normal social sign-in flow. Better Auth 1.6.25 supports provider-level `disableSignUp`, `disableImplicitSignUp`, `disableIdTokenSignIn`, `getUserInfo`, and `mapProfileToUser`; the sign-in request supports explicit `requestSignUp`. `emailAndPassword.requireEmailVerification` also exists in 1.6.25, but is limited to email/password sessions. The provider-level social `requireEmailVerification` and `user.validateUserInfo` gates were added later and are absent from the pinned 1.6.25 provider types. ([v1.6.25 init options](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/core/src/types/init-options.ts), [v1.6.25 provider type](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/core/src/oauth2/oauth-provider.ts), [later changelog](https://github.com/better-auth/better-auth/blob/main/packages/core/CHANGELOG.md), accessed 2026-09-27.)
- In `1.6.25`, OAuth sign-in computes the creation gate as `(disableImplicitSignUp && !requestSignUp) || disableSignUp`. The `requestSignUp` field is accepted by the OAuth sign-in request. Thus `disableImplicitSignUp: true` blocks the default implicit creation but can be overridden by an explicit signup request; `disableSignUp: true` is the stronger provider-side gate. The account-linking handler applies that gate only when it finds no matching local user, so already linked Google accounts continue to sign in. ([sign-in source](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/better-auth/src/api/routes/sign-in.ts), [callback source](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/better-auth/src/api/routes/callback.ts), [account-linking source](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/better-auth/src/oauth2/link-account.ts), tag `v1.6.25`, accessed 2026-09-27.)
- When Google returns an identity not yet linked to a local user, Better Auth can find a local user by email and implicitly link the provider account. The current implementation requires a verified provider email unless that provider is trusted, and requires `localUser.emailVerified=true` by default (`requireLocalEmailVerified ?? true`). If those conditions fail, it returns `account_not_linked`; it does not create another user for the matched local record. `trustedProviders` bypasses the provider-email-verification check, so adding Google there intentionally broadens trust. ([version-pinned account-linking source](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/better-auth/src/oauth2/link-account.ts), accessed 2026-09-27.)
- Google supplies the signed OIDC `email_verified` claim. Better Auth 1.6.25 maps it to `user.emailVerified`; its implicit account-linking code requires that provider claim and a locally verified user by default. The email/password `requireEmailVerification` option does not gate this social callback; the corresponding per-provider social gate was added later. ([Google provider source v1.6.25](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/core/src/social-providers/google.ts), [link-account source v1.6.25](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/better-auth/src/oauth2/link-account.ts), [per-provider option changelog](https://github.com/better-auth/better-auth/blob/main/packages/core/CHANGELOG.md), accessed 2026-09-27.)
- In the pinned release, an explicit Google signup can create a user whose `emailVerified` reflects a false Google claim and still return a social session; the Hub's email signup also permits an unverified session today. The email/password option does not change this provider path. If product wants verified-only Google signup, stop for a separate pre-creation guard or reviewed upgrade; do not treat the password-only flag as a social gate. ([Google mapper v1.6.25](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/core/src/social-providers/google.ts), [callback v1.6.25](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/better-auth/src/api/routes/callback.ts), [per-provider option changelog](https://github.com/better-auth/better-auth/blob/main/packages/core/CHANGELOG.md), accessed 2026-09-27.)
- `account.accountLinking.disableImplicitLinking: true` rejects same-email OAuth sign-in when that provider identity is not already linked, even if the provider is trusted or the email is verified. Authenticated users can still link deliberately with `linkSocial()`. This option prevents implicit linking, not new user signup; pair it with `disableSignUp: true` for an existing-user-only posture. The defaults for `allowDifferentEmails` and `updateUserInfoOnLink` are respectively `false` and `false`, which retain same-email linking and prevent provider profile edits on link. ([User & Accounts docs](https://better-auth.com/docs/concepts/users-accounts), [options reference](https://better-auth.com/docs/reference/options), accessed 2026-09-27.)
- Google says to use the stable, never-reused `sub` claim as the provider identifier, not email. `email_verified` indicates email verification; `hd`, not the email's apparent domain, identifies a Google Workspace/Cloud hosted domain. Google also documents signature, issuer, audience, and expiry validation for ID tokens. ([Google OIDC reference](https://developers.google.com/identity/openid-connect/reference), [Google OIDC sign-in guide](https://developers.google.com/identity/openid-connect/openid-connect), accessed 2026-09-27.)

## Security evidence and OAuth controls

Better Auth published a high-severity advisory on 2026-05-31 for pre-account hijacking through OAuth implicit linking. An attacker could pre-register an unverified password account using a victim's email; older versions then linked the victim's verified OAuth identity and left the attacker's password usable. The advisory marks versions before `1.6.11` affected and says the fix rejects linking to local accounts whose email is unverified. It also says `requireEmailVerification` alone did not mitigate the old flaw. Hub's pinned `1.6.25` is beyond the affected range; keep the local verification gate enabled and do not opt out with `requireLocalEmailVerified: false`. ([Better Auth security advisory, published 2026-05-31](https://github.com/better-auth/better-auth/security/advisories/GHSA-g38m-r43w-p2q7).)

For the OAuth transaction, RFC 9700 (January 2025) calls for exact redirect-URI matching, protection against open redirects, authorization-code flows with PKCE, and transaction-bound CSRF protection using PKCE or OIDC `nonce` (otherwise a securely bound one-time `state`). Use PKCE `S256`. OWASP's OAuth cheat sheet also recommends Authorization Code with PKCE and marks the implicit grant deprecated. ([RFC 9700, published January 2025](https://www.rfc-editor.org/rfc/rfc9700.html), [OWASP OAuth 2.0 Cheat Sheet, accessed 2026-09-27](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html).)

For Google specifically, request only the identity scopes needed (`openid email profile` if the app needs all three); validate the signed ID token's issuer, audience, expiry, and signature. If restricting Workspace domains, validate the returned `hd` claim; a request parameter or the `email` domain is not a substitute. Keep the post-login destination on an allowlist. Hub already documents a narrow internal return-path validator for `/comprar/<slug>`; RFC 9700 supports exact redirect matching and rejects arbitrary return URLs. ([Google OIDC guide](https://developers.google.com/identity/openid-connect/openid-connect), [RFC 9700 §2.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1), both accessed 2026-09-27; Hub context: [`identity-and-authorization.md`](../docs/domain/identity-and-authorization.md).)

## Recommendation after the product clarification

1. Configure Google with `disableImplicitSignUp: true`. `/entrar` starts social sign-in without `requestSignUp`; `/cadastro` sends `requestSignUp: true` only for an explicit registration action. Do not set provider-wide `disableSignUp: true`, which would block the clarified registration path.
2. Keep `AUTH_PUBLIC_SIGNUP_ENABLED` as the server-side gate for both email and social signup. It defaults to `false`; when false, both are closed. When true, the login UI still omits `requestSignUp`, while the registration UI may send it. Treat that field as explicit signup intent, not as unforgeable proof that the browser is physically on `/cadastro`.
3. Keep implicit linking only under Better Auth's verified-provider and verified-local-email checks. Do not disable the local check, add Google to `trustedProviders` to bypass the provider claim, or turn off implicit linking globally.
4. Preserve guest-first purchase: do not add login, social login or account creation before payment. Only the authoritative payment flow creates/reuses the account and grants course access.
5. Resolve the paid-account activation gap: Asaas-created users start with `emailVerified=false`; Better Auth 1.6.25 consumes the one-time reset token and writes the credential but does not mark the user verified. `onPasswordReset` can mark the email verified after the token succeeds, but runs after the password write; test a partial failure and provide a safe retry path.
6. Google `sub` remains the durable external identity; email is only an initial lookup. A narrow lookup may compare the Google address and `normalizeBuyerEmail` result, but may use a local `users.id` only when exactly one candidate exists. Preserve `allowDifferentEmails=false` and `updateUserInfoOnLink=false`; never choose between collisions or merge users.
7. Add a unique database invariant for `(provider_id, account_id)` before enabling Google. The Hub schema has only an index by `user_id`; Better Auth 1.6.25 looks up the provider/account pair and inserts links, so callbacks can race without a unique index. Audit duplicates first and stop for manual review if any exist.
8. Keep OAuth callback destinations internal. `/api/auth/redirect` returns JSON for the email form; add a browser continuation for OAuth, reuse role/block policy, and preserve only `getSafeAuthReturnTo` destinations.
9. Update paid-access notification selection so a configured, linked Google account counts as a usable sign-in method; do not send a password-activation email solely because `provider_id='credential'` is absent.
10. Do not turn on global email-password verification as a shortcut for Google.
    The pinned 1.6.25 does expose `emailAndPassword.requireEmailVerification`,
    but it only gates password sign-ins; it does not gate Google social sessions.
    The current email signup UI also expects an immediate session. Keep global
    verification off for this feature and provide a verification-only fallback
    when an existing local email/password user requests a Google link.

The reset-password handler in pinned Better Auth `1.6.25` consumes the email token and creates or updates the credential account, then calls `onPasswordReset`; it does not set `emailVerified`. The callback runs after the credential write, not atomically with it. The existing reset UI then sends the user to `/entrar`, so the flow needs a tested recovery path and clear instructions. ([version-pinned password route](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/better-auth/src/api/routes/password.ts), [Hub auth config](../src/lib/auth.ts), [reset form](<../src/app/(auth)/redefinir-senha/reset-password-form.tsx>), [activation delivery](../src/features/outbox/delivery.ts), accessed 2026-09-27.)

Better Auth 1.6.25 exposes an async Google `mapProfileToUser` hook before local OAuth-user lookup. It can map only an unambiguous existing candidate to the stored email while preserving the provider's `sub` and `emailVerified` claim. For an already-linked `sub`, preserve the account-first path even if Google changes the email; canonical email matching is only for first-time linking. This mapping must be tested against the pinned callback implementation and fail closed on multiple candidates. ([Google provider source](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/core/src/social-providers/google.ts), [provider option type](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/core/src/oauth2/oauth-provider.ts), [account-first lookup](https://github.com/better-auth/better-auth/blob/v1.6.25/packages/better-auth/src/db/internal-adapter.ts), accessed 2026-09-27.)

### Global email verification versus targeted proof

- The Hub's current `auth.ts` has no `emailVerification` sender and no
  `emailAndPassword.requireEmailVerification`. Email signup creates an
  unverified local row but immediately creates a session; the current signup UI
  then calls `/api/auth/redirect`, and the free-course flow depends on that
  session.
- Better Auth 1.6.25 supports the password-only
  `emailAndPassword.requireEmailVerification` option. Enabling it makes the
  email signup response skip auto sign-in and requires a verification sender;
  the Hub's current signup form would treat the absent session as an error. The
  setting does not gate Google social sign-in. The social-provider
  `requireEmailVerification` option is a later API and is absent from the
  pinned 1.6.25 provider types.
- Better Auth 1.6.25 already exposes `/send-verification-email`, which can send
  a verification link to an unverified local email without requiring a global
  signup gate and returns a non-enumerating response for unknown/already
  verified emails. The Hub can configure the sender but leave automatic
  `sendOnSignUp` and `sendOnSignIn` disabled, then invoke the endpoint only when
  an account-linking attempt needs proof.
- A user who already has an email/password session can also explicitly link a
  provider through Better Auth's `linkSocial`; the pinned callback requires a
  verified provider claim and same-email match by default, but does not require
  the local row's `emailVerified` flag on the explicit authenticated-link path.
  The Hub has no account-security UI for that action today.

**Recommendation:** do not globally gate sign-up or password sign-in in the
Google-login change. Preserve the current guest checkout and immediate signup
contract; mark the paid account verified only after its one-time email
activation succeeds. Add a generic, opt-in email-verification path for legacy
local rows rejected by implicit OAuth linking, or a clear explicit-link action
after password authentication. Do not mark `email_verified=true` on payment.

**Plan boundary:** the Google provider is already included in the installed Better Auth package, so no package install is indicated. A database migration is now recommended for provider/account uniqueness; do not apply it outside Development without separate authorization. This research did not inspect deployed Google client settings or run a live OAuth callback. The feature stays unavailable until client credentials are configured per environment and callback URIs are registered exactly.

## Better Auth maintainer and issue history

- Issue [#6392](https://github.com/better-auth/better-auth/issues/6392), opened 2025-11-28, requested explicit `linkSocial()` while blocking silent same-email linking. Maintainer PR [#7270](https://github.com/better-auth/better-auth/pull/7270) merged 2026-01-27 and added `disableImplicitLinking`; its documented behavior preserves explicit authenticated linking but still permits OAuth signup, hence the need for the separate `disableSignUp` gate.
- Issue [#10215](https://github.com/better-auth/better-auth/issues/10215), opened 2026-06-25, asked whether `disableImplicitLinking` was a supported public option. Documentation PR [#10218](https://github.com/better-auth/better-auth/pull/10218) merged the same day, documenting it in User & Accounts and the options reference after checking the implementation. This closes the earlier documentation gap.
- The security advisory above records the pre-account-hijacking flaw and patch boundary; it is more authoritative for the verified-local-email requirement than older issue comments or examples.

## Not verified

- Whether deployed Hub auth settings already configure Google, `disableSignUp`, or trusted providers; only the pinned package and canonical identity documentation were checked.
- Whether Supabase currently exposes a dedicated setting that disables social signup without disabling sign-in; the reviewed identity-linking and general-configuration pages did not establish that behavior.
- Whether every Google email variation corresponds to exactly one local user under the Hub buyer normalizer. Reuse the existing read-only buyer-identity collision audit; do not infer identity from a string or merge collisions.
- Whether Hub's password-reset callback and `email_verified` write can be made atomic with current Better Auth integration; the callback is after credential persistence, so the implementation needs a retryable recovery path.
