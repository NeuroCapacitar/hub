# Pesquisa: upload de imagens, progresso visível e recarregamento

**Verificado em:** 24/09/2026. Pesquisa documental em fontes primárias oficiais e inspeção somente leitura do worktree indicado.

## Contexto observado no projeto

- `bun.lock` resolve Next.js `16.3.3`, React/React DOM `19.2.7` e `@aws-sdk/client-s3` mais `@aws-sdk/s3-request-presigner` `3.1073.0`.
- `src/features/storage/staged-image-upload-client.ts` prepara a referência, envia o `File` por `fetch`/PUT direto ao R2, tenta o fallback autenticado por `POST` se o PUT falhar e só então chama a confirmação. `src/features/storage/r2.ts` gera o PUT assinado com `PutObjectCommand`, assina `Content-Type` e usa expiração de dez minutos.
- As galerias de Banner e mídia de acesso apresentam toast e item temporário/skeleton; o formulário de Certificado conta uploads pendentes. O cliente compartilhado não expõe callback de bytes enviados. A galeria de Banner também usa `URL.createObjectURL(file)` para preview.
- Os itens administrativos de Banner e mídia de acesso usam `BannerImage` com `unoptimized`. O guia R2 do projeto registra que a URL pública da mídia de acesso inclui uma versão derivada de `updated_at`.

## Progresso de bytes e feedback de fase

O `fetch()` usado hoje aceita `File` como corpo e retorna uma `Promise<Response>`. O Fetch Standard contém processamento interno de blocos do corpo, mas sua assinatura pública não oferece à aplicação um evento/callback de progresso do upload. Esta conclusão sobre a API pública é uma inferência da especificação; ela não afirma que o navegador deixe de acompanhar internamente os bytes. Em contraste, `XMLHttpRequest.upload` expõe eventos `progress` para acompanhar o envio. [WHATWG Fetch Standard, atualizado em 2026-09-21](https://fetch.spec.whatwg.org/#fetch-method) · [MDN: Using the Fetch API, consultado em 2026-09-24](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch) · [WHATWG XMLHttpRequest Standard, consultado em 2026-09-24](https://xhr.spec.whatwg.org/#the-upload-attribute) · [MDN: XMLHttpRequest.upload, atualizado em 2025-08-26](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest/upload)

Uma porcentagem só é determinada quando `ProgressEvent.lengthComputable` é verdadeiro e `total` é positivo; nesse caso, `loaded / total` representa a fração transferida. `loaded` mede o corpo da mensagem HTTP, sem cabeçalhos e outros overheads. No elemento HTML `<progress>`, fornecer `value` cria progresso determinado; omiti-lo representa progresso indeterminado. [WHATWG XMLHttpRequest: ProgressEvent, consultado em 2026-09-24](https://xhr.spec.whatwg.org/#interface-progressevent) · [MDN: ProgressEvent, consultado em 2026-09-24](https://developer.mozilla.org/en-US/docs/Web/API/ProgressEvent) · [WHATWG HTML: progress, consultado em 2026-09-24](https://html.spec.whatwg.org/multipage/form-elements.html#the-progress-element)

**Implicação para o fluxo atual:** se a UI precisar de porcentagem por bytes, instrumentar com XHR o PUT direto (e, se desejado, o fallback que também envia o arquivo). Exibir `loaded / total` somente nesse trecho. Preparar URL, aguardar resposta, confirmar por `POST`, validar/processar a imagem e salvar/publicar são fases distintas; apresentar essas esperas como a mesma porcentagem daria uma medida que o evento não fornece. Manter uma mensagem/fase indeterminada, como “Preparando”, “Enviando”, “Confirmando imagem” e “Salvando”, até a confirmação e a mutação final terminarem. O evento `loadend` sozinho não indica sucesso; tratar erro/abort e verificar o status HTTP, além do resultado da confirmação. [WHATWG XMLHttpRequest: eventos de progresso, consultado em 2026-09-24](https://xhr.spec.whatwg.org/#interface-progressevent) · fluxo observado em `staged-image-upload-client.ts` e nas galerias administrativas.

Atualizar estado React a partir dos eventos é suficiente para renderizar a interface: `useState` agenda nova renderização quando seu setter recebe o novo valor. [React: useState, consultado em 2026-09-24](https://react.dev/reference/react/useState)

Ao observar `XMLHttpRequest.upload`, listeners devem ser registrados antes do envio e pedidos cross-origin passam por preflight CORS. Para o R2, a política deve cobrir origem, método e headers enviados; headers de resposta como `ETag` precisam de `ExposeHeaders` para leitura via JavaScript. A política documentada pelo projeto já permite PUT e `Content-Type`; incluir `Cache-Control`, checksum ou metadata no PUT exige revisar a assinatura e `AllowedHeaders`. URLs pré-assinadas expiradas retornam erro sem headers CORS no R2, então o navegador não consegue ler o corpo desse erro. [MDN: XMLHttpRequest.upload](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest/upload) · [Cloudflare R2: CORS, atualizado em 2026-09-23](https://developers.cloudflare.com/r2/buckets/cors/) · política atual em `docs/integrations/r2.md`.

URLs pré-assinadas R2 autorizam uma operação sobre um objeto, são bearer tokens, usam o domínio da API S3 e não funcionam em custom domains. Cloudflare documenta PUT direto pelo navegador, restrição opcional de `Content-Type` na assinatura e expiração de 1 segundo a 7 dias; o código do projeto fixa dez minutos. A documentação AWS JavaScript v3 confirma o padrão de SDK `PutObjectCommand` + `getSignedUrl`; as restrições de R2 acima vêm da documentação Cloudflare, que é a autoridade para o serviço utilizado. [Cloudflare R2: Presigned URLs, atualizado em 2026-08-22](https://developers.cloudflare.com/r2/api/s3/presigned-urls/) · [AWS SDK for JavaScript v3: exemplos S3, consultado em 2026-09-24](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/javascript_s3_code_examples.html)

## Recarregamento e cache de imagens

Cache HTTP associa respostas a URLs e pode reutilizá-las sem consultar o servidor. Para conteúdo imutável, URL com versão/hash mais `max-age` longo e `immutable` permite cache eficiente. Para conteúdo mutável no mesmo URL, `no-cache` permite armazenamento, mas exige validação antes de reutilizar; `no-store` evita armazenar a nova resposta, porém não apaga uma resposta antiga já armazenada. Portanto, um novo `key` React não invalida cache HTTP, CDN ou cache do otimizador; para substituir bytes com segurança, mudar a URL/versão ou definir revalidação apropriada. [MDN: HTTP caching, consultado em 2026-09-24](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching) · [React: reset de estado com `key`, consultado em 2026-09-24](https://react.dev/reference/react/useState)

No Next.js atual, o otimizador de `next/image` usa TTL mínimo padrão de quatro horas, combinado com o maior valor entre esse mínimo e o `Cache-Control` da origem; não há mecanismo de invalidação desse cache. A documentação recomenda mudar `src` ou remover o arquivo otimizado em cache. `unoptimized` serve a origem diretamente, sem passar pelo otimizador. Assim, o TTL do Next aplica-se às imagens otimizadas; nos itens administrativos do projeto que passam `unoptimized`, a frescura depende da URL e dos headers/cache HTTP ou Cloudflare. [Next.js: Image Component, consultado em 2026-09-24](https://nextjs.org/docs/app/api-reference/components/image) · [Next.js 16: guia de atualização e TTL padrão, consultado em 2026-09-24](https://nextjs.org/docs/app/guides/upgrading/version-16)

Para objetos públicos R2, cache de borda requer custom domain; `r2.dev` é destinado a desenvolvimento e não oferece cache. A documentação também alerta que conteúdo servido pelo cache pode não refletir imediatamente a versão mais recente. R2 suporta `Cache-Control` como metadata HTTP do objeto. Isso favorece URLs versionadas quando a imagem muda, mantendo cache longo apenas para objetos cujo conteúdo não será sobrescrito. [Cloudflare Cache: habilitar cache em R2, atualizado em 2026-05-07](https://developers.cloudflare.com/cache/interaction-cloudflare-products/r2/) · [Cloudflare R2: como funciona, consultado em 2026-09-24](https://developers.cloudflare.com/r2/how-r2-works/) · [Cloudflare R2: upload e metadata HTTP, atualizado em 2026-07-29](https://developers.cloudflare.com/r2/objects/upload-objects/) · [Cloudflare R2: compatibilidade S3, consultado em 2026-09-24](https://developers.cloudflare.com/r2/api/s3/api/)

**Implicação para o projeto:** a URL pública de mídia de acesso já carrega versão baseada em `updated_at`, alinhada à estratégia de URL versionada. Para qualquer superfície que mantenha a mesma URL após substituir bytes, verificar tanto a identidade do `src` quanto headers do endpoint e cache de borda; `router.refresh()` ou remontar o componente não é, por si, purge de cache. Os previews locais criados com `URL.createObjectURL(file)` não são URL de R2; revogar cada object URL quando o preview deixar de ser usado libera o recurso associado. [MDN: File API e object URLs, consultado em 2026-09-24](https://developer.mozilla.org/en-US/docs/Web/API/File_API/Using_files_from_web_applications) · `docs/integrations/r2.md` · `src/app/api/banners/[bannerId]/image/route.ts` · `src/features/banners/banner-image.tsx`.
